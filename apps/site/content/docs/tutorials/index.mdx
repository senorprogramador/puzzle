## API maturity

The [package readiness audit](https://github.com/senorprogramador/puzzle/blob/main/docs/api-stability-audit.md)
records the source/export checks, executed tests, and limitations behind these labels.

- **Stable:** validated API with an explicit backward-compatibility commitment.
  Button, ButtonGroup and ToggleGroup (including Item) are Stable. The Auth
  tutorial uses the Stable Button API.
- **Beta:** implemented and tested, but may evolve. Storage adapters,
  Auth/Session/Fullstack, and SEO utilities/components/adapters used here
  remain Beta; other UI primitives retain their component-specific labels.
- **Experimental:** insufficient validation evidence for the public surface.
  These tutorials do not require Experimental APIs. Existing Experimental UI
  components elsewhere in the reference retain that classification.

No tutorial claims that a Beta API is Stable or that passing tests establishes
production readiness. Review the [Auth security requirements](/docs/auth/security)
before deploying authentication.

## How to follow the examples

Code-block titles are application-relative file paths. Keep the indicated
directory layout so relative imports work. Framework alternatives are alternatives,
not extra metadata writers to install alongside the standalone server.

The examples target TypeScript with strict checking and React 19. Bun is an
explicit runtime choice for the standalone servers and Argon2id implementation,
not a requirement of the Puzzle library contracts. Existing Next.js or TanStack
applications can reuse the server modules through the adapters shown in the guides.

The repository's `test:tutorials` check extracts the named TypeScript blocks,
checks imports against built package export maps, and typechecks them together.
It also runs the pure SEO rendering assertions and notebook behavior checks.
Real database conformance and framework/deployment checks are distinguished
from those example checks in each tutorial.

From a repository checkout, build packages first and run the example check:

```bash
bun run build
bun run --filter '@puzzle-ui/site' test:tutorials
bun run --filter '@puzzle-ui/site' build
bun run --filter '@puzzle-ui/site' test:hydration
```

Set `TUTORIAL_MONGODB_URI` to a **disposable** transaction-capable MongoDB fixture
to include the notebook and Auth flows. Set `TUTORIAL_SITE_URL` to a running
local documentation build to also check rendered routes, metadata, JSON-LD,
sitemap and `llms.txt`. These checks copy built package output into a temporary
consumer project, so workspace source aliases cannot hide packaging mistakes.
They remove that project afterward and never install additional dependencies.
The hydration check uses the existing Playwright Chromium installation and
starts/stops its own production server on an ephemeral local port. It checks
fresh loads, client navigation, history and reloads for hydration errors,
duplicate metadata/JSON-LD and stale route entities.
